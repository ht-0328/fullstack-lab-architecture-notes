01結論: リクエストは 3 つの門を通る

「認証」と「認可」は別の仕事で、このリポジトリでは別のコンポーネントが受け持ちます。守りは 3 段で、画面のボタンの出し分けは守りに含めません。

門 1 ・ Nginx + oauth2-proxy

ログイン済みか？
Nginx は転送する前に auth_request で oauth2-proxy に Cookie を見せる。oauth2-proxy が Cookie を復号できれば 202 と JWT を返し、できなければ 401。AWS では ALB の認証アクションがこの門。
落ちると: 画面は 302 でログイン画面へ、/bff/* は 401 の JSON

門 2 ・ BFF

その JWT は本物か？
前段を信じ切らず、Keycloak の公開鍵で署名を検証し、iss・aud・exp を確かめる。知らない発行元は拒否。通ったら CurrentUser（sub、種別、ロール）を組み立てる。
落ちると: 401。スモークテストは偽の JWT を BFF に直接送って 401 を確認している

門 3 ・ 認可 API

この操作をしてよいか？
BFF が主体（sub、種別、ロール）・操作（task:read など）・対象（所有者）を送り、allowed と理由を受け取る。既定で拒否。認可 API が落ちたら 503 で拒否（fail-closed）。
落ちると: 登録は 403、他人の詳細は 404（存在を知らせない）

02登場人物と役割

Keycloak は「ユーザーを預かり、パスワードを確認し、JWT を発行する」役だけです。ログイン画面へ飛ばしたり Cookie を持ったりはせず、それは oauth2-proxy の仕事。JWT を検証するのは BFF、可否を決めるのは認可 API。同じ Nuxt と BFF を一般利用者と社員で共有し、入口のホスト名でだけ経路が分かれます。

03Keycloak の中身

Keycloak の用語は多いですが、このリポジトリで使っているのは次の 12 個だけです。右の列がこのリポジトリでの具体名です。

用語何かこのリポジトリでは
realmユーザー・クライアント・ロール・署名鍵・設定をまとめた、独立した区画。realm が違えばユーザーも鍵も別で、トークンの iss も realm ごとに変わる。customer（一般利用者。本番も Keycloak）と staff（Okta の代替）。定義は auth/keycloak/import/customer-realm.json と keycloak/import/staff-realm.json
clientrealm に登録した「ログインに使うアプリ」。redirect URI、シークレット、どのフローを許すかを持つ。fullstack-lab-customer（oauth2-proxy-customer が使う）、fullstack-lab-staff、auth-api（認証 API が使う）
client secretconfidential client がトークン交換のときに提示する秘密。.env の CUSTOMER_CLIENT_SECRET / STAFF_CLIENT_SECRET / AUTH_API_CLIENT_SECRET。realm JSON はプレースホルダーで受け取る
standard flow認可コードフロー。ブラウザを Keycloak のログイン画面へ飛ばし、戻ってきたコードを裏側でトークンに交換する。PKCE はコードの横取り対策。oauth2-proxy が実行する（OAUTH2_PROXY_CODE_CHALLENGE_METHOD: S256）。図 4
service account（client_credentials）人ではなくアプリ自身がトークンを得る方式。ログイン画面は出ない。auth-api に有効。realm-management の manage-users / view-users / view-realm を持つ。図 8
realm rolerealm 内で定義する役割。JWT の realm_access.roles に出る。customer。会員登録時に認証 API が付与する。BFF は読み取るが、一般利用者の認可には使わない（所有者で判定する）
groupユーザーの集まり。Okta の「グループ」に相当。realm staff の task-viewer（carol）と task-admin（dave）。認可 API の staff-role-permissions のキーと一致させる
protocol mapperトークンにどのクレームを、どの名前で入れるかの定義。audience（aud に client ID を入れる。BFF の aud 検証用）、groups (Okta 互換)（グループ名を groups に入れる。full.path=false なので task-admin と出る）
署名鍵 / JWKSrealm ごとの鍵ペア。秘密鍵で JWT に署名し、公開鍵を /protocol/openid-connect/certs で配る。BFF（jwk-set-uri）と oauth2-proxy（OIDC_JWKS_URL）が http://keycloak:8080/realms/…/certs から取る
access token lifespanアクセストークンの寿命。両 realm とも 300 秒。oauth2-proxy が 4 分ごとに refresh_token で更新する（COOKIE_REFRESH: 4m）。Cookie 自体は 8 時間
Admin REST API/admin/realms/{realm}/users などの管理 API。ユーザー作成、ロール付与、パスワード再設定ができる。認証 API（KeycloakAdminClient.kt）だけが呼ぶ。BFF や画面からは直接触らない
hostname の 2 面性ブラウザから見た URL とコンテナ間の URL が違う。iss はブラウザ側の URL で発行される。ブラウザ: http://localhost:8180、コンテナ間: http://keycloak:8080。KC_HOSTNAME と KC_HOSTNAME_BACKCHANNEL_DYNAMIC: true で両方を受け付ける。BFF は issuer-uri と jwk-set-uri を別々に設定

開発モードの注意。 Keycloak は start-dev --import-realm で起動し、起動のたびに realm JSON を取り込みます。会員登録で作ったユーザーも、コンテナを作り直すと消えます。realm の設定を変えたら docker compose up -d --force-recreate keycloak です。

04ログインの流れ

最初に http://localhost:8080/ を開いてから、ログイン後の画面が出るまで。4 つの段階があり、Keycloak が出てくるのは B と、D の公開鍵の取得だけです。

  1. ①ブラウザが localhost:8080 を開く。まだ Cookie は無い。
  2. ②Nginx は転送する前に、そのホスト用の oauth2-proxy-customer に「この人はログイン済みか」を聞く（auth_request）。本文は渡さず、Cookie だけを見せる。
  3. ③Cookie _fsl_customer が無いので 401。
  4. ④画面のパスなので、Nginx はログイン開始の URL へリダイレクトする（/bff/* なら 401 の JSON を返す）。
  5. ⑤ブラウザがログイン開始を要求する。/oauth2/* は Nginx がそのまま oauth2-proxy に渡す。
  6. ⑥oauth2-proxy が「認可コードフロー」を始める。state と PKCE の code_challenge（S256）を付けて、http://localhost:8180/realms/customer/protocol/openid-connect/auth へ飛ばす。ここで初めて Keycloak が登場する。
  7. ⑦ログイン画面は Keycloak のもの（URL は localhost:8180）。alice が ID とパスワードを入れる。パスワードを受け取るのは Keycloak だけで、Nginx も BFF も知らない。
  8. ⑧認証に成功すると、Keycloak は使い捨ての「認可コード」を付けて、client fullstack-lab-customer に登録された redirect URI（localhost:8080/oauth2/callback）へ戻す。
  9. ⑨ブラウザがコードを oauth2-proxy に届ける。
  10. ⑩oauth2-proxy がコンテナ間の URL http://keycloak:8080/realms/customer/protocol/openid-connect/token に、コード・PKCE の code_verifier・client secret を送る。ブラウザを通らない「裏側」の通信。
  11. ⑪Keycloak が 3 つのトークンを返す。access_token が、この後ずっと BFF へ渡される JWT（有効期限 5 分）。
  12. ⑫oauth2-proxy はトークン一式を暗号化して Cookie _fsl_customer に入れ、元のページへ戻す。ブラウザが持つのはこの暗号化 Cookie だけで、JWT そのものは見えない。
  13. ⑬もう一度 / を開く。今度は Cookie がある。
  14. ⑭Nginx が再び oauth2-proxy に確認する。
  15. ⑮Cookie を復号できたので 202。応答ヘッダーに access_token（JWT）を載せて Nginx に渡す。
  16. ⑯Nginx はその JWT を x-amzn-oidc-accesstoken ヘッダーに入れて Nuxt へ転送する。ALB が付けるのと同じヘッダー名。ブラウザが同名ヘッダーを送ってきても Nginx が必ず上書きする。
  17. ⑰SSR 中の Nuxt は http://bff:8080 を直接呼ぶ。Nginx を通らないので、JWT とリクエスト ID は Nuxt 自身が引き継ぐ。
  18. ⑱BFF は JWT の iss を見て検証器を選び、http://keycloak:8080/realms/customer/protocol/openid-connect/certs（JWKS）から公開鍵を取る。以後はキャッシュ。署名・iss・aud・exp を確かめる。
  19. ⑲検証済み JWT から CurrentUser（sub、表示名、CUSTOMER、ロール）を組み立て、画面の出し分け用の情報を返す。
  20. ⑳ログイン後の画面が描かれる。以後 4 分ごとに oauth2-proxy がトークンを更新し、新しい Cookie を Nginx 経由でブラウザへ返す（Cookie 自体は 8 時間）。

ブラウザが持っているのは JWT ではなく、暗号化された Cookie です。 JWT は oauth2-proxy が Cookie を復号したときに現れ、Nginx がヘッダーに載せて後段へ渡します。だから DevTools の Cookie 欄を見ても JWT は読めません。見るなら、ログイン後に /swagger/ から /bff/me を呼ぶと、BFF が JWT から組み立てた利用者情報が返ります。

Keycloak の URL が 2 つあるのはなぜか。 ブラウザが開くログイン画面と、トークンの iss は http://localhost:8180。oauth2-proxy がコードを交換するときと、BFF が公開鍵を取るときはコンテナ間の http://keycloak:8080。ブラウザは keycloak という名前を解決できず、コンテナは localhost:8180 が自分自身を指してしまうためです。AWS では IdP が公開 URL ひとつになるので、この区別は消えます。

05JWT の中身と、誰がどこを見るか

JWT は「ヘッダー.ペイロード.署名」を Base64URL でつないだ文字列です。ペイロードは誰でも読めますが、署名があるので改ざんできません。alice のアクセストークンは、おおよそ次の形です（値は例。他にも項目があります）。

// ヘッダー（署名の方式と、使った鍵の ID）
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "…（realm の鍵の ID）"
}
// ペイロード（クレーム）
{
  "iss": "http://localhost:8180/realms/customer",
  "sub": "…（Keycloak が採番したユーザー ID）",
  "aud": "fullstack-lab-customer",
  "azp": "fullstack-lab-customer",
  "exp": 1761800300,   // iat + 300 秒
  "iat": 1761800000,
  "typ": "Bearer",
  "preferred_username": "alice",
  "realm_access": { "roles": ["customer", …] }"groups": ["task-admin"]
}
// 署名: realm の秘密鍵で ヘッダー.ペイロード に署名したもの
署名 + kidBFFJWKS から kid の公開鍵を取り、署名を検証する。ここで偽造が落ちる。oauth2-proxy も受け取り時に同じ検証をする
issBFFどの発行元用の検証器を使うかを選ぶ。登録の無い iss は拒否。利用者の種別（CUSTOMER）もここで決まる。ホスト名ではなく iss で判断する
audBFFfullstack-lab-customer を含むか。同じ Keycloak が別のアプリ向けに出したトークンを拒否するため。realm の audience mapper が入れている
expBFF期限切れなら 401。寿命 5 分だが、oauth2-proxy が 4 分ごとに更新するので普段は切れない
subBFF認可 API利用者 ID。認可 API に送る主体の id になり、タスクの createdBy と比べて所有者かを判定する。パスワード変更の対象 ID にも使う（他人の ID を指定できない）
preferred_usernameBFF表示名（nameClaim）。守りには使わない
realm_access.rolesBFF認可 APIロールの置き場所は IdP で違う。Keycloak は realm_access.roles、Okta は groups。BFF が roles-claim の設定で吸収して roles に揃える。一般利用者は所有者で判定するので、ロールは判定に使わない。社員は task-admin に付いた操作が許される。
読まない人NginxNuxtAPINginx と Nuxt は中身を見ずに運ぶだけ。API は BFF を信頼し、JWT を受け取らない（API でも検証する多層防御は発展課題）

06認可の流れ

ログイン済みの alice がタスク 1 の詳細を開くときの、BFF の内側です。BFF は「対象を取る → 認可 API に聞く → 許可なら続きを取る」の順で動き、拒否なら API を呼びません。

  1. ①詳細画面のデータを取る。ブラウザからの fetch でも、SSR 中の Nuxt からでも、BFF 以降は同じ。
  2. ②Nginx が Cookie を oauth2-proxy に確認させる。
  3. ③セッション有効。JWT が返る。
  4. ④Nginx が JWT をヘッダーに載せて BFF へ。
  5. ⑤門 2。BFF が署名（公開鍵）・iss・aud・exp を検証する。iss から CUSTOMER、realm_access.roles からロールを取り出す。失敗したら 401 で終わり。
  6. ⑥まず対象を取る。API は BFF を信頼していて、自分では認証も認可もしない（入口からは 404 で到達できない）。
  7. ⑦タスクには登録した人の sub が入っている。これが「所有者」。
  8. ⑧門 3。BFF が認可 API に問い合わせる。送るのは主体 {id: sub, userType: CUSTOMER, roles: [customer]}、操作 task:read、対象 {type: task, ownerId}。
  9. ⑨認可 API は Policy.kt で判定する。一般利用者なら ownerId == sub のときだけ許可（理由: customer owns the resource）。どれにも当てはまらなければ拒否。
  10. ⑩許可されたときだけ、続きの API（外部カレンダーの補足）を呼び、画面用に集約する。
  11. ⑪詳細が返る。
  12. ⑫拒否なら API は呼ばず、詳細は 404、登録は 403 を返す。認可 API 自体が落ちているときは 503 で拒否する（fail-closed）。

判定表（authz の application.yml と Policy.kt）

ロール名（task-viewer、task-admin）は IdP 側が付け、「そのロールで何ができるか」は認可 API 側の設定が持ちます。一般利用者はロールではなく所有者で判定します。

072 つのホスト、2 つの realm、1 つの BFF

一般利用者と社員で違うのは入口だけです。Nginx がホスト名で oauth2-proxy を選び、oauth2-proxy が realm を選びます。BFF は「どのホストから来たか」を知らず、JWT の iss だけで種別を決めます。

08会員登録とパスワード変更（認証 API）

ここまでの登場人物はログインしか扱いません。ユーザーを「作る」「パスワードを変える」のは認証 API（auth/）の仕事で、Keycloak の Admin REST API を代行して呼びます。ログイン自体は担当しません。

  1. ①/signup の画面から送る。ログインしていないので Cookie は無い。
  2. ②public-locations.conf の 3 つ（/signup、/bff/signup、/_nuxt/）だけは認証なしで通す。ただし localhost のホストだけで、admin.localhost には無い。認証ヘッダーは空にして渡す。
  3. ③BFF 側も SecurityConfig でこのパスだけ permitAll。他は全部 JWT 必須。
  4. ④BFF は publish された auth-client で認証 API を呼ぶ。主体が無いので認可 API には聞かない。
  5. ⑤認証 API は人ではなく「アプリ自身」として Keycloak にログインする。client auth-api とそのシークレット（AUTH_API_CLIENT_SECRET）を送る。
  6. ⑥Admin API 用のトークン。認証 API は期限の 30 秒前まで使い回す。
  7. ⑦Admin REST API でユーザーを作る（username = email、emailVerified = true、パスワード）。auth-api には realm-management の manage-users / view-users が付いているので許される。
  8. ⑧Keycloak が採番した ID が Location ヘッダーで返る。この ID が、ログイン後の JWT の sub になる。
  9. ⑨realm ロール customer を付ける。失敗したらユーザーを削除して、登録をやり直せる状態に戻す。
  10. ⑩契約（auth.yaml）の形で返す。
  11. ⑪画面は「ログインする」の導線を出す。以後は図 2 のいつものログインに入る。

パスワード変更は門を全部通る

  1. ①ログイン済みの一般利用者が POST /bff/me/password を呼ぶ。Nginx の auth_request と BFF の JWT 検証を通る（門 1、門 2）。
  2. ②BFF が認可 API に account:change-password を聞く。対象の ownerId には JWT の sub を使うので、他人のアカウントを指定する余地が無い（門 3）。社員は customer-actions にしか無い操作なので 403 になり、認証 API は呼ばれない。
  3. ③認証 API が「現在のパスワード」を確かめる。やり方は、そのユーザー名とパスワードで Keycloak のトークンエンドポイントに grant_type=password を投げ、トークンが取れるかどうか。invalid_grant なら不一致で 403。
  4. ④一致したら Admin API の PUT /users/{id}/reset-password で新しいパスワードを設定する。
