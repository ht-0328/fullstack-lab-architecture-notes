01結論: ログインは 5 つの役で回る

ログインの正体は「窓口で身分証をもらい、確認係がそれを札に包んでブラウザに持たせる」ことです。2 回目からは札を見せるだけで通れます。受付はそのたびに確認係へ「この札は有効？」と聞いてから、奥の部屋へ案内します。

02登場人物と、まず覚える言葉

図の例えと、実際の名前の対応です。以後の図でも同じ役割には同じアイコンと色を使います。

  • あなた（ブラウザ）
  • 札 = Cookie（ブラウザが持つ）
  • 受付 = Nginx（URL を見て案内）
  • 確認係 = oauth2-proxy（札の発行と確認）
  • 窓口 = Keycloak（本人確認）
  • 身分証 = JWT（窓口が出す）
  • 画面 = Nuxt
  • BFF（身分証を検める）
  • API（データ）

まず覚える言葉（8 つ）

  • Cookie（札）サーバーが「次に来るとき見せて」とブラウザに持たせる小さなメモ。ブラウザは同じサイトへ行くたびに自動で添える。ここでは「ログイン済み」の札
  • キャッシュCookie と混同しやすい別物。同じものを取りに行かないための保存で、速さのためにある。Cookie は「誰か（前と同じ人か）」を伝えるためにある
  • Nginx（受付）全部のリクエストを最初に受け、URL（ホスト名とパス）を見て奥の Nuxt や BFF に渡す。渡す前に確認係へ「ログイン済み？」と聞く。AWS では ALB がこの役
  • oauth2-proxy（確認係）ログインの手続きを丸ごと引き受ける小さなプログラム。初回は窓口へ案内して札を作り、2 回目からは札が有効かを答える。アプリ自身は手続きを知らずに済む
  • Keycloak（窓口）ユーザーを預かり、ID とパスワードを確かめ、身分証を出す本人確認の窓口。一般には IdP（Identity Provider）と呼ぶ。社員向けは AWS で Okta になる
  • JWT（身分証）窓口が出す身分証。「誰か、いつまで有効か」が書かれ、偽造できない印（署名）つき。札の中に包まれて運ばれ、奥の部屋の BFF が検める
  • セッション「ログイン済み」の状態が続いていること。札（Cookie）がその証。札の期限が切れると、もう一度窓口へ行く
  • OAuth2 と OIDC手続きの名前。OAuth2 は「許可を取る」仕組みで、その上に「ログイン」を載せたものが OIDC。oauth2-proxy が窓口と話すときに使うのは OIDC

次に読むページ。ここまで分かれば 認証・認可の図解 が読めます。あちらでは、受付と確認係が「門 1」、BFF が「門 2」、認可 API（してよいかを決める係）が「門 3」として出てきます。

層 2流れ初めて来たときと、2 回目から。各節の先頭に要約

03初めて来たとき: 札をもらうまで

札を持っていないあなたが画面を開いてから、札をもらうまでです。窓口に行くのはこの 1 回だけで、パスワードを受け取るのも窓口だけです。

  1. 札が無い受付が確認係に聞くと「札が無い」。受付はあなたを窓口へ案内する
  2. 窓口で本人確認あなたが窓口で ID とパスワードを入れる。受付も確認係もパスワードを見ない
  3. 引換券を持って戻る窓口は身分証を直接は渡さず、引換券（code）をくれる。あなたはそれを確認係に渡す
  4. 札をもらう確認係が引換券を窓口で身分証に換え、札に包んであなたに渡す。以後はこの札で通る

042 回目から: 札で通る

札を持っているあなたが画面を開くときです。窓口には行きません。確認係が札を開けて身分証を取り出し、受付がそれを奥の部屋へ付けて渡します。

  1. 札つきで受付へブラウザが自動で札を添える。あなたは何もしない
  2. 受付が確認係に聞く「この札、有効？」。受付は自分では札を開けない
  3. 確認係が身分証を返す札を開けて中の身分証を受付に渡す。期限が近ければ裏で新しい札に替える
  4. 身分証を付けて奥へ受付が身分証を付けて渡す。奥の BFF が身分証を検めてから仕事をする

06よくある誤解

初めて見たときにつまずきやすい点です。

5 つの誤解を開く
  • 「Cookie はキャッシュのようなもの？」違います。キャッシュは「同じものを取りに行かないための保存」で速さのため。Cookie は「あなたが誰か（前と同じ人か）」をサーバーに伝えるための札です。消すと速さは変わらず、ログインが外れます。
  • 「ブラウザは JWT を持っている？」持っていません。持っているのは暗号化された札（Cookie）で、開けられるのは確認係だけです。DevTools の Cookie 欄を見ても JWT は読めません。
  • 「Nginx がログインを確認している？」していません。受付は確認係に「有効？」と聞いて、答えに従うだけです。札を確かめるのは確認係、本人確認（パスワード）をするのは窓口です。
  • 「OAuth と書いてあるのに、ログイン（認証）に使うの？」OAuth2 は本来「許可を取る」仕組みですが、その上に「ログイン」を載せた OIDC（OpenID Connect）があり、oauth2-proxy はそれを使います。名前に oauth2 と付いているだけで、やっていることはログインの代行です。
  • 「ログインできたら、何でもできる？」できません。身分証が答えるのは「誰か」だけです。「この操作をしてよいか」は別の係（認可 API）が決めます。認証・認可のページの「門 3」です。
このページは一般的な仕組みの説明で、fullstack-lab の設定が変わっても変わりません。例として挙げた名前と値（Cookie 名、寿命、ヘッダー名）は 2026-10-30 時点の fullstack-lab のもので、認証・認可の図解 と合わせて直します。
