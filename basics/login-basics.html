01結論: ログインは 5 つの役で回る

ログインの正体は、Keycloak（窓口）で本人確認をして JWT（身分証）をもらい、oauth2-proxy（確認係）がそれを Cookie（札）に包んでブラウザに持たせることです。2 回目からは Cookie を見せるだけで通れます。Nginx（受付）はそのたびに oauth2-proxy へ「この Cookie は有効？」と聞いてから、奥のアプリへ渡します。

02登場人物と、まず覚える言葉

図に出てくるものの実際の名前と、括弧の中が例えです。以後の図でも同じ役割には同じアイコンと色を使います。

  • あなた（ブラウザ）
  • Cookie（札）。ブラウザが持つ
  • Nginx（受付）。URL を見て渡す先を決める
  • oauth2-proxy（確認係）。Cookie の発行と確認
  • Keycloak（窓口）。本人確認
  • JWT（身分証）。Keycloak が出す
  • Nuxt。画面
  • BFF。JWT を確かめる
  • API。データを出す

まず覚える言葉（8 つ）

  • Cookie（札）サーバーが「次に来るとき見せて」とブラウザに持たせる小さなメモ。ブラウザは同じサイトへ行くたびに自動で添える。ここでは「ログイン済み」を示すもの
  • キャッシュCookie と混同しやすい別物。同じものを取りに行かないための保存で、速さのためにある。Cookie は「誰か（前と同じ人か）」を伝えるためにある
  • Nginx（受付）全部のリクエストを最初に受け、URL（ホスト名とパス）を見て奥の Nuxt や BFF に渡す。渡す前に oauth2-proxy へ「ログイン済み？」と聞く。AWS では ALB がこの役
  • oauth2-proxy（確認係）ログインの手続きを丸ごと引き受ける小さなプログラム。初回はブラウザを Keycloak へ案内して Cookie を作り、2 回目からは Cookie が有効かを答える。アプリ自身は手続きを知らずに済む
  • Keycloak（窓口）ユーザーを預かり、ID とパスワードを確かめ、JWT を出す。一般には IdP（Identity Provider）と呼ぶ。社員向けは AWS で Okta になる
  • JWT（身分証）Keycloak が出す身分証。「誰か、いつまで有効か」が書かれ、偽造できない署名つき。Cookie の中に包まれて運ばれ、BFF が署名を確かめる
  • セッション「ログイン済み」の状態が続いていること。Cookie がその証。Cookie の期限が切れると、もう一度 Keycloak でログインする
  • OAuth2 と OIDC手続きの名前。OAuth2 は「許可を取る」仕組みで、その上に「ログイン」を載せたものが OIDC。oauth2-proxy が窓口と話すときに使うのは OIDC

次に読むページ。ここまで分かれば 認証・認可の図解 が読めます。あちらでは、Nginx と oauth2-proxy が「門 1」、BFF が「門 2」、認可 API（操作してよいかを決める API）が「門 3」として出てきます。

層 2流れ初めて来たときと、2 回目から。各節の先頭に要約

03初めて開いたとき: Cookie をもらうまで

Cookie を持っていないブラウザで画面を開いてから、Cookie をもらうまでです。Keycloak に行くのはこの 1 回だけで、パスワードを受け取るのも Keycloak だけです。

  1. Cookie が無いNginx が oauth2-proxy に聞くと「Cookie が無い」。ブラウザは Keycloak のログイン画面へリダイレクトされる
  2. Keycloak で本人確認あなたが Keycloak の画面で ID とパスワードを入れる。Nginx も oauth2-proxy もパスワードを見ない
  3. 認可コードを持って戻るKeycloak は JWT を直接は渡さず、認可コード（code）を返す。ブラウザはそれを oauth2-proxy に渡す
  4. Cookie をもらうoauth2-proxy が認可コードを Keycloak で JWT に交換し、Cookie に包んでブラウザに渡す。以後はこの Cookie で通る

042 回目から: Cookie で通る

Cookie を持っているブラウザで画面を開くときです。Keycloak には行きません。oauth2-proxy が Cookie を復号して JWT を取り出し、Nginx がそれを付けて BFF へ渡します。

  1. Cookie つきで Nginx へブラウザが自動で Cookie を添える。あなたは何もしない
  2. Nginx が oauth2-proxy に聞く「この Cookie、有効？」。Nginx は自分では Cookie を復号しない
  3. oauth2-proxy が JWT を返すCookie を復号して中の JWT を Nginx に渡す。JWT の期限が近ければ、裏で Keycloak から新しい JWT をもらい、Cookie を作り直す
  4. JWT を付けて BFF へNginx が JWT をヘッダーに付けて渡す。BFF は JWT の署名を確かめてから処理する

06よくある誤解

初めて見たときにつまずきやすい点です。

5 つの誤解を開く
  • 「Cookie はキャッシュのようなもの？」違います。キャッシュは「同じものを取りに行かないための保存」で速さのため。Cookie は「あなたが誰か（前と同じ人か）」をサーバーに伝えるためのものです。消すと速さは変わらず、ログインが外れます。
  • 「ブラウザは JWT を持っている？」持っていません。持っているのは暗号化された Cookie で、復号できるのは oauth2-proxy だけです。DevTools の Cookie 欄を見ても JWT は読めません。
  • 「Nginx がログインを確認している？」していません。Nginx は oauth2-proxy に「有効？」と聞いて、答えに従うだけです。Cookie を確かめるのは oauth2-proxy、本人確認（パスワード）をするのは Keycloak です。
  • 「OAuth と書いてあるのに、ログイン（認証）に使うの？」OAuth2 は本来「許可を取る」仕組みですが、その上に「ログイン」を載せた OIDC（OpenID Connect）があり、oauth2-proxy はそれを使います。名前に oauth2 と付いているだけで、やっていることはログインの代行です。
  • 「ログインできたら、何でもできる？」できません。JWT が答えるのは「誰か」だけです。「この操作をしてよいか」は認可 API が決めます。認証・認可のページの「門 3」です。
このページは一般的な仕組みの説明で、fullstack-lab の設定が変わっても変わりません。例として挙げた名前と値（Cookie 名、寿命、ヘッダー名）は 2026-10-30 時点の fullstack-lab のもので、認証・認可の図解 と合わせて直します。
