01結論: AWS アカウントは入れ物。入り方は 3 通り

AWS アカウントは、リソース（ECR、ECS、RDS など）と請求をまとめる入れ物で、例えるならビル 1 棟です。人は、root ユーザー（オーナー）、IAM ユーザー（合鍵）、IAM ロール（入館証）のどれかとしてアカウントに入ります。root ユーザー以外は、ポリシー（許可の紙）に書かれた操作しかできません。

02登場人物と、まず覚える言葉

実際の名前と、01 の図で使った例えの対応です。03 からは実際の名前だけで書き、同じ役割には同じアイコンを使います。

  • AWS アカウント（ビル）
  • root ユーザー（オーナー）
  • IAM ユーザー（合鍵）
  • IAM ロール（入館証。一時的）
  • ポリシー（許可の紙）
  • Organizations（複数アカウントの管理）
  • アクセスポータル（IAM Identity Center）
  • 社員（会社の人）

まず覚える言葉（8 つ）

  • AWS アカウントリソースを入れる入れ物で、請求書が届く単位。ログイン ID のことではない（例えるならビル 1 棟）
  • アカウント IDアカウントを区別する 12 桁の数字。アカウント名は表示用の名前で、あとから変えられる
  • root ユーザーアカウントを作ったときにできる持ち主。サインアップに使ったメールとパスワードで入る。何でもでき、誰にも制限できない
  • IAM ユーザーアカウントの中に作る、人ごとのログイン ID。パスワードでコンソールに入る。ずっと有効
  • IAM ロール持ち主のいない権限のまとまり。許された人や仕組み（GitHub Actions など）が一時的に切り替えて使い、時間がたつと失効する
  • ポリシー「どのリソースに何をしてよいか」を書いた JSON。IAM ユーザー、グループ、ロールに付ける。書いていないことはできない
  • MFAパスワードに加えて、パスキーや認証アプリで本人だと示す仕組み（多要素認証）
  • Organizations複数の AWS アカウントをまとめて管理する仕組み。会社で環境ごとにアカウントを分けるときに使う

コンソール右上の表示の読み方。上の行の「アカウント名（12 桁の ID）」はどのアカウントか、下の行（例: Administrator）は誰として入っているかです。root ユーザーで入っているときは、下の行が出ません。アカウント名に root などの文字が入っていても、それは表示用の名前で、root ユーザーで入っているという意味ではありません。

03アカウントを作ったら最初にやること

AWS アカウントを作った直後は、サインアップに使ったメールとパスワードでログインする root ユーザーしかいません。root ユーザーは何でもできるので、乗っ取られると被害が大きくなります。そこで最初に次の 4 つを行い、以後の作業は root ユーザーではなく、自分用に作った IAM ユーザーで行います。

  1. アカウントを作るサインアップすると、アカウントと root ユーザーができる。プランと支払い方法もここで決める
  2. root ユーザーに MFA を付けるパスワードが漏れても、パスキーなどが無ければ入れないようにする
  3. 予算アラートを作るBudgets で月の予算を決め、超えそうならメールを受け取る。通知だけで、課金は止まらない
  4. 自分用の IAM ユーザーを作る管理者のグループに入れ、MFA を付ける。以後はこれでログインする
手順の細かい点を開く サインアップから IAM ユーザーで入り直すまで
  1. 1サインアップでは、root ユーザーのメール、アカウント名（表示用の名前。あとから変えられる）、パスワード、プラン（Free / Paid）、連絡先、支払い方法、電話の確認、サポートプランを入れます。サポートプランは無料のベーシックで足ります。
  2. 2root ユーザーの MFA は、右上のメニューの「セキュリティ認証情報」で付けます。MFA の名前はあとから変えられないので、直したいときは新しく登録してから古いほうを消します。2 つ目を登録するには、MFA を使ってログインし直したセッションが要ります。
  3. 3予算アラートは「Billing and Cost Management」→「予算」で作ります。請求や IAM の画面は、リージョンに関係しない「グローバル」なサービスなので、右上のリージョンが選べなくなります。
  4. 4IAM ユーザーは、管理者の権限を付けても、最初は請求の画面を見られません。root ユーザーで「アカウント」の画面を開き、「IAM ユーザーおよびロールによる請求情報へのアクセス」を有効にします。
  5. 5IAM ユーザーを作ると、そのアカウント専用のサインイン URL（https://<アカウント ID>.signin.aws.amazon.com/console）が出ます。IAM ユーザーはこの URL から入ります。root ユーザーは、ログイン画面の「ルートユーザーの E メールを使用したサインイン」から入ります。

04IAM ロールは何に使うか

アプリ（ECS のタスク）や GitHub Actions に AWS を操作させるときは、IAM ユーザーを作らず、IAM ロールを使います。「アプリにロールを付与すると、アプリがロールを持つので操作できる」と考えたくなりますが、ロールはアプリに渡してずっと持たせるものではありません。アプリや GitHub Actions は、操作するたびに AWS STS（一時的な認証情報を発行するサービス）からそのロールの期限つきの認証情報をもらい、ロールとして操作します。

この「ロールの認証情報をもらって、ロールとして操作する」ことを、このページでは「ロールに切り替える」と書きます（AWS の用語では「ロールを引き受ける」、英語で assume role）。切り替えている間は、AWS からはロールとして見え、使えるのはロールの権限だけです。IAM ユーザーのアクセスキーには期限が無く、漏れると無効にするまで使われ続けますが、ロールなら期限つきの認証情報しか渡らないので、人以外の仕組みにはロールを使います。

  1. ロールを作る「誰が切り替えてよいか」（信頼ポリシー）と「何をしてよいか」（許可のポリシー）の 2 つを決める
  2. 切り替えを頼む決められた相手が、自分が誰かを示して切り替えを頼む。受け付けるのは AWS STS（一時的な認証情報を発行するサービス）
  3. 期限つきの認証情報が返る期限（GitHub Actions なら既定 1 時間）が来ると使えなくなる
  4. 許された操作だけをする許可のポリシーに書いた操作だけができる

次の表は、何がロールに切り替えるかと、そのときに自分が誰かをどう示すかを並べたものです。fullstack-lab の列は、どのフェーズで出てくるかを示します。

ロールに切り替えるもの何をするか（例）自分が誰かの示し方fullstack-lab では
GitHub Actionsイメージを ECR に push し、ECS を更新するGitHub が発行する JWT（OIDC）を STS に渡すフェーズ 3 で作る予定
ECS のタスクECR からイメージを取り込み、ログを送る。アプリが AWS のサービスを呼ぶECS がタスクにロールを渡す（タスク実行ロール、タスクロール）フェーズ 4 で作る予定

次の表は、ロールについて思い込みやすい理解と、実際の仕組みの対応です。ECS のタスクのような AWS のサービスについては「ロールを付ける」で合っていますが（AWS のコンソールも「割り当てる」と書く）、GitHub Actions や IAM ユーザーに「付与する」、ロールを「持っている」は、仕組みとしては正確ではありません。

思い込みやすい理解正しいか実際の仕組み
ECS のタスクにロールを付ける正しいタスク定義にロールの ARN を書き、ロールの信頼ポリシーで「ECS のタスクは切り替えてよい」と許す。ECS が自動でロールに切り替え、認証情報の更新も自動で行う。AWS のコンソールでも「ロールを割り当てる」と書かれる
GitHub Actions にロールを付与する不正確GitHub には鍵も権限も渡さない。AWS 側のロールの信頼ポリシーに「このリポジトリの main は切り替えてよい」と書き、ワークフローは実行のたびに GitHub の JWT を見せてロールに切り替える
ロールを持っているから操作できる不正確ずっと持っているのではなく、操作するたびに期限つきの認証情報をもらう。期限が切れたら、もらい直す（ECS は自動、GitHub Actions は実行ごと）
IAM ユーザーにロールを付与する間違いそういう設定は無い。ロールの信頼ポリシーで「このユーザーは切り替えてよい」と許し、ユーザーが自分で切り替える（コンソールでは「スイッチロール」）
ロールを使うと、自分の権限にロールの権限が足される間違い切り替えている間は、ロールの権限だけで動く。自分（IAM ユーザー）の権限は使わない。同時に使えるロールは 1 つだけ

切り替える前と後で、AWS から「誰として見えているか」が変わります。次は、IAM ユーザー Administrator が ecr-push というロール（例）に切り替えたときの、aws sts get-caller-identity（今の自分が誰かを表示するコマンド）の出力です。

# 切り替える前
aws sts get-caller-identity
#   Arn: arn:aws:iam::<ID>:user/Administrator          ← IAM ユーザーとして見える

# ecr-push に切り替えて、もらった認証情報で実行したあと
aws sts get-caller-identity
#   Arn: arn:aws:sts::<ID>:assumed-role/ecr-push/…     ← ロールとして見える

コンソールで「スイッチロール」したときも同じで、右上の表示がユーザー名からロール名に変わります。期限が切れると、その認証情報は使えなくなります。

細かい流れは、作るときに。GitHub Actions が JWT を使ってロールに切り替える細かい流れ（OIDC）は、フェーズ 3 で実際に作るときに、別のページで説明します。

05会社ではアカウントを複数持つ

会社では、開発・検証・本番のように、環境ごとに AWS アカウントを分けることが多いです。アカウントが別なら、開発での操作ミスが本番に届かないためです。アカウントは Organizations でまとめ、社員は IAM Identity Center のアクセスポータルから各アカウントに入ります。

  1. 親のアカウントが子のアカウントを作るOrganizations の管理アカウント（親）から子のアカウントを作る。親には請求と管理だけを置く
  2. メールは別名で足りるアカウントごとに root 用のメールが要るが、aws+dev1@… のような別名で 1 つの受信箱に集める
  3. 社員はアクセスポータルにログインする会社の IdP（Okta など）でログインすると、入れるアカウントと権限の一覧が出る
  4. 選んだアカウントにロールで入る「開発 1 に開発者の権限で」を選ぶと、そのアカウントのロールに切り替えて入る。IAM ユーザーは作らない
個人（今の fullstack-lab）会社（一般的な形）
アカウントの数1 つ。環境は Terraform のコードの中で分ける環境やシステムごとに複数。Organizations でまとめる
root 用のメール自分のメール 1 つアカウントごとの別名（aws+dev1@…）。受信箱は共有の 1 つ
人の入り方IAM ユーザーアクセスポータルでロールに切り替える
仕組みの入り方どちらも IAM ロール（GitHub Actions、ECS のタスクなど）

業務環境とのつながり。業務環境のアカウントの分け方と、社員が AWS にどう入っていたかは、まだ分かっていません。この節は一般的な形で、業務環境の事実ではありません。分かったら、fullstack-lab の docs/architecture/ の「仮定」に足してから、ここも合わせます。

2026 年から、AWS には「プロジェクト」を作る新しいサインアップ形式があり、従来の形式とかなり違います。

07権限の決まり方

ある操作をしてよいかは、ポリシーをいくつか重ねて決まります。

判定の順番を開く IAM ポリシー、SCP、RCP、root ユーザーの例外
  1. 1どこかに「拒否（Deny）」と書いてあれば、拒否です。許可がいくつあっても、拒否が勝ちます。
  2. 2Organizations の禁止ルール（SCP。人や仕組みができることの上限）と、リソース側の禁止ルール（RCP。リソースに誰が触れるかの上限）が許していなければ、拒否です。単独のアカウントには、どちらも掛かっていません。
  3. 3IAM ユーザー・ロールに付けたポリシー（グループ経由を含む）か、リソースに付けたポリシーに「許可（Allow）」と書いてあれば、許可です。
  4. 4どこにも書いていなければ、拒否です（既定は拒否）。
だれIAM ポリシーで縛れるかSCP で縛れるか
root ユーザー縛れない組織の子のアカウントなら縛れる。単独のアカウントや管理アカウントでは縛れない
IAM ユーザー縛れる組織の子のアカウントなら縛れる
IAM ロール縛れる（許可のポリシーと、切り替えてよい相手を決める信頼ポリシーの 2 つ）組織の子のアカウントなら縛れる

fullstack-lab の認可 API と同じく、「書いていなければ拒否」が基本です。新しいサインアップ形式で OIDC プロバイダを作れなかったのは、2 の SCP に拒否が書いてあったためで、自分の IAM ポリシーでは解除できません。

08よくある誤解

初めてアカウントを作ったときにつまずきやすい点です。

8 つの誤解を開く
  • 「アカウント = ログイン ID？」違います。AWS のアカウントは、リソースと請求の入れ物です。ログインするのは、その中の root ユーザー、IAM ユーザー、または切り替えた先のロールです。
  • 「IAM ユーザーにロールを付ける？」付けません。Keycloak のロールはユーザーに付けるラベルですが、IAM ロールはユーザーとは別の ID です。IAM ユーザーがロールを使うときは、一時的にそのロールに切り替え（コンソールでは「スイッチロール」）、その間はロールの権限だけで動きます。切り替えるには、ロールの信頼ポリシーとユーザー側のポリシー（sts:AssumeRole）の両方で許されている必要があります。ECS のタスクや Lambda には「ロールを付ける」と言い、その場合は AWS が自動でそのロールに切り替えて動かします。
  • 「アカウント名に root と入っているから、root で入っている？」違います。アカウント名は表示用の名前です。誰として入っているかは、右上の 2 行目を見ます。root ユーザーで入っているときは 2 行目が出ません。
  • 「AdministratorAccess を付ければ、請求も見られる？」最初は見られません。root ユーザーで「IAM ユーザーおよびロールによる請求情報へのアクセス」を有効にして、初めて見られます。
  • 「アカウントはプロジェクトごとに作るもの？」決まりはありません。個人の学習なら 1 つで足ります。会社では環境やシステムごとに分けることが多く（05）、新しいサインアップ形式では「プロジェクト = アカウント」です。
  • 「アカウントを増やすたびにメールボックスを作る？」作らずに済みます。aws+dev1@… のような + の別名は、対応しているメール（Gmail、Microsoft 365 など）なら、事前の作成なしに元の受信箱へ届きます。
  • 「アカウント ID は秘密？」AWS は、アカウント ID を秘密情報としては扱っていません。ただし出す必要もないので、fullstack-lab ではリポジトリに書かず、Terraform や CI が実行時に取ります。
  • 「Organizations は個人でも使うべき？」必須ではありません。使うと、管理アカウントにはリソースを置かないのが AWS の勧める形です。なお、Free プランのアカウントは、Organizations に入ると Paid プランに変わります。
