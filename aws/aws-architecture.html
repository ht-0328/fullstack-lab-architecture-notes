01全体の構成

アプリ側（Nginx、Nuxt、BFF、認可 API、認証 API、API、WireMock）はローカルと同じ 7 つがそのまま ECS on Fargate のタスクになります。差し替わるのは入口（Nginx + oauth2-proxy → ALB）、IdP（Keycloak の realm staff → Okta）、DB（コンテナ → RDS）です。

ローカルと変わらないもの。門 2（BFF での JWT 検証）と門 3（認可 API の判定）はコードも設定も同じです。ALB が付けるヘッダー名 x-amzn-oidc-accesstoken はローカルの Nginx がすでに同じ名前で付けているので、BFF は違いを知りません。認証・認可の中身は 認証・認可の図解 にあります。

層 2流れを追うALB の認証、CI/CD、まだ決めていないこと

02ALB の認証: ホストごとのリスナールール

ローカルで Nginx の server ブロックと oauth2-proxy が分担していた「振り分け」と「認証」は、AWS では ALB のリスナールールにまとまります。ルールは Host と Path の条件に、認証アクションの有無と IdP を組み合わせたものです。認証アクションは HTTPS リスナーでしか使えないため、ドメインと ACM の証明書が必須になります。

03CI/CD と成果物の流れ

この規模では GitHub Actions だけで CI/CD は完結します。CodeBuild は「使うために使う」のではなく、AWS の内側で実行する必要がある処理（本番用イメージの ECR への push、VPC 内での RDS のマイグレーション、CodeArtifact への publish）だけを受け持ちます。Actions は長期のアクセスキーを持たず、OIDC で IAM ロールを引き受けて一時的な認証情報を得ます。

04未決の点

図は docs/aws-roadmap.md の既定（Terraform、Nginx を置くパターン A）で描いています。フェーズ 3 以降に着手する前に、次を決めます。

  1. IaC は Terraform と CDK のどちらにするか（図は Terraform を仮定）
  2. ALB の認証に使うドメインを持っているか（無ければ Route 53 で取得。年 15 ドル前後）
  3. AWS 上の Keycloak を ECS で自前運用する（案 a）か、既存のものを使う想定で Cognito などで代用する（案 b）か。Okta は Developer アカウントで本物を使うか
  4. Nginx の配置。ALB → Nginx → Nuxt / BFF のパターン A（図）か、ALB のパスルールで直接振り分けるパターン B か
  5. 常時稼働か、学習するときだけ作って終わったら壊す運用か（24 時間 365 日で月 165〜225 ドル程度、作っては壊すなら 1 回 1〜2 ドル程度）
